# dsherp 首次技术验证计划

> 执行方式：在当前任务中顺序执行。采用 executing-plans 工作方式；不默认委派子 Agent。

**目标：** 确定可以复现的 DSH SDK / Runtime 与 ERPNext 技术基线，为首条业务链提供证据。

**架构：** 独立 Python 服务驱动 DSH 子进程，通过受限工具连接隔离 ERPNext 测试站点。此计划只覆盖技术验证，不实现完整 SaaS 或制造业务。

**技术方向：** Python、DSH SDK、Frappe / ERPNext。准确版本由下述核验产出，不预填未经确认的版本号。

**设计：** ../specs/2026-08-28-dsherp-design.md

## 全局约束

- 不修改现有 AgenERP，不复用访问现有生产数据的凭证。
- 不安装或启动服务，直至执行本计划且完成资源读取检查；需要真实模型调用时仅使用用户授权的凭证和费用范围。
- 不自动下载大体积镜像、不停止既有容器；涉及资源占用先盘点并说明。
- 临时资料放 work/，证据不得包含密钥和业务敏感内容。
- 不把技术验证完成报告成业务系统完成。

## 任务 1：确定依赖与运行契约

产出：docs/engineering/runtime-baseline.md。

- [x] 检查本机 Python、Node、包管理器、Docker、可用资源和端口，只读，不改变现有环境。
- [x] 查询官方发布和包元数据，选择 DSH SDK 与匹配 Runtime，并记录准确版本、来源与上游提交。
- [x] 阅读该版本 Python SDK 的完整最小示例及 Runtime 启动要求，记录实际导入、会话、事件和关闭接口。
- [x] 读取同版本工具扩展资料，确认受限 ERP 工具如何注册和运行；不假设 SDK 任意支持 Python 回调。
- [x] 选择兼容的 Frappe / ERPNext 版本组合，查证自制和委外业务方法；记录镜像或包的固定标识。
- [x] 对照设计检查工具限制、租户隔离与关闭行为是否能实现；发现不支持项直接报告，不以替代演示掩盖。

完成标准：基线文档能逐项追溯来源，明确哪些是文档核对、哪些已运行；没有虚构的 API 或兼容性结论。

## 任务 2：验证最小 DSH 会话

产出：基线确认后，在独立实施计划中定义最小可运行脚本、准确 SDK 调用、依赖锁和测试文件。

- [x] 基于任务 1 的真实接口编写 TDD 计划：缺失配置立即报错、事件正确消费、异常退出不残留进程。
- [x] 先执行失败测试，再实现最小 SDK 调用和正常关闭逻辑。
- [ ] 使用明确授权的模型凭证运行一条无 ERP 写入的任务，记录版本、命令、退出状态及脱敏事件。
- [x] 验证 Runtime 只开放本阶段需要的工具；不能仅凭配置文件存在就声称权限已生效。

完成标准：有真实模型调用与正常关闭证据；若缺少凭证，明确标记真实调用未验证。

## 任务 3：验证隔离 ERPNext 接口

产出：docs/engineering/erpnext-integration-evidence.md。

- [x] 选择新建隔离测试环境的部署方式、端口和资源预算，不复用未知用途的现有站点。
- [ ] 记录测试 Site、版本和合成数据来源，不在仓库保存密钥。

- [ ] 验证一个受限工具通过真实 ERPNext API 返回可核对记录；无权读取时明确拒绝。

完成标准：真实只读调用成功和权限拒绝均有证据；不使用管理员查询结果替代普通用户权限验证。
