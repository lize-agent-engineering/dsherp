
# dsherp 前端与 Agent 业务应用生成规划

> 2026-08-29：实施方向已由 [原生上下文 Agent 计划](2026-08-29-context-agent-sidebar.md) 替代。本文件保留历史，不再作为独立工作台、双空间导航、任意代码生成或破坏性修改的实施授权。旧 Demo 保留独立入口，不再扩展。

## 一、方向与范围


**Agent 不仅生成页面，还要生成可运行的业务应用：数据结构、页面、业务逻辑、权限、菜单及相应测试。** 用户通过预览确认业务效果，管理员确认后发布。

采用以下分工：

- **Frappe/ERPNext**：业务数据、原生动态页面、角色权限、现有业务规则和单据生命周期。
- **dsherp**：需求理解、应用构建交互、变更预览、隔离验证、发布管理及 Agent 业务操作。
- **交付方式**：先完成可操作的前端流程，再按流程接入后端与 Agent，不提前搭建全系统。
- **首版设备**：仅桌面网页。
- **生成方式**：优先配置原生能力；配置不足时，Agent 生成自定义 App 代码并测试，由管理员确认发布。不要求每次都有开发人员参与。
- **结构变更**：包括新增、修改、删除、类型转换和已有数据迁移，不缩减为只能新增字段。

原生 Workflow 可承担条件和角色审批；自定义代码用于原生配置不能表达的逻辑。不直接采用尚未在当前 v15 中提供的能力，例如文档标注为 v16 的 Workflow Transition Tasks。[Workflow](https://docs.frappe.io/erpnext/workflows)、[版本边界](https://docs.frappe.io/erpnext/workflow-transition-tasks)

## 二、前端划分与菜单

产品分为 **企业工作端、平台管理端**。企业工作端包含业务使用空间和应用构建空间，两者共用账号、企业上下文和导航，不拆成多个独立产品。

### 1. 公共账号入口

负责用户进入正确的企业和身份环境。

| 页面 | 功能 |
|---|---|
| 登录与账号恢复 | 登录、退出、找回密码、会话失效提示 |
| 企业选择 | 展示已加入企业及其开通状态，进入或切换企业 |
| 创建企业 | 填写必要信息、发起开通、查看失败原因 |
| 接受邀请 | 查看邀请企业与身份，确认加入 |
| 个人设置 | 个人资料、语言、安全设置 |

统一身份优先复用 Frappe 的认证能力，不自写密码系统。平台维护跨企业成员关系，各业务 Site 保留对应用户和独立权限；不能把相同邮箱直接当作跨站点授权依据。

### 2. 企业工作端：业务使用空间

面向企业员工、主管和业务管理人员。

**固定菜单保持精简，具体业务菜单由已发布应用生成。**

| 固定入口 | 功能 |
|---|---|
| 工作台 | 我的待办、待确认事项、近期任务和常用应用；不堆砌无业务价值的统计卡片 |
| Agent 助手 | 查询资料、发起业务、查看执行过程、补充信息、打开关联单据 |
| 我的待办 | Frappe 工作流任务、分配任务，以及 Agent 执行前的业务确认；标明来源 |
| 业务应用 | 按当前用户权限显示企业已发布的 Workspace 和业务页面 |
| 任务记录 | 查看 Agent 任务的成功、失败、部分成功及实际业务结果 |
| 企业设置 | 对有权限的成员开放企业信息、成员和角色管理入口 |

动态业务菜单不预先固定成完整 ERP 模块树。例如企业发布“设备维修”应用后，可以出现：

```text
业务应用
└─ 设备维修
   ├─ 报修记录
   ├─ 我的维修任务
   └─ 维修统计
```

这些页面优先由 DocType、原生视图和 Workspace 生成。需要专门操作体验时，才增加自定义页面。

**页面可见性不代替数据权限**：打开链接、查询关联记录、读取字段和执行动作仍由服务端检查。

### 3. 企业工作端：应用构建空间

面向被授权的业务设计者、企业管理员和发布者。

| 菜单 | 功能 |
|---|---|
| 应用目录 | 查看已发布应用、构建中的应用；新建应用或修改现有应用 |
| 构建工作区 | 用对话描述需求，Agent 发现现有对象、提出复用和扩展方案 |
| 发布与变更 | 查看待发布版本、影响范围、确认发布、失败处理及恢复记录 |

每个应用内部设置以下标签页，不把它们全部铺成全局菜单：

| 标签页 | 内容 |
|---|---|
| 需求与方案 | 用户需求、尚未确定的问题、业务流程和验收场景 |
| 页面与导航 | 列表、表单、详情、报表及菜单预览 |
| 数据结构 | 对象、字段、关联、子表，以及与当前版本的差异 |
| 业务规则 | 校验、计算、状态转换、审批、跨单据动作和定时任务 |
| 角色权限 | 谁能看、修改、提交、取消，以及记录和字段范围 |
| 测试预览 | 隔离环境中按不同角色操作，查看测试数据和结果 |
| 版本与发布 | 当前版本、候选变更、数据迁移影响、发布状态与历史 |

普通用户可以提出需求，但不能因此取得结构修改或代码发布权限。

### 4. 平台管理端

面向 dsherp 平台运营和运维人员，不作为企业业务操作后台。

| 菜单 | 功能 |
|---|---|
| 租户管理 | 企业列表、企业详情、开通状态、服务状态 |
| 开通与部署任务 | Site 创建、环境准备、版本部署及失败处理 |
| 运行与资源 | 租户服务状态、资源占用、Agent 运行异常 |
| 发布运行记录 | 查看部署技术状态和恢复记录，不默认读取客户业务内容 |
| 平台成员与权限 | 管理平台运营、运维和管理员权限 |
| 操作记录 | 记录开通、部署、权限及其他平台操作 |

首版不增加计费套餐、应用市场、外部连接器市场或通用运维门户。

### 5. 原生高级管理入口

Frappe 已有的用户、角色、权限配置、字段定制和工作流编辑页面继续保留，由有权限的人员访问。

不额外建设一套等价管理页面。对已纳入应用版本管理的对象，发布前重新检查实际配置，发现原生后台产生的变更时展示冲突，不静默覆盖。

## 三、生成、执行与发布架构

### 1. 界面实现

- 原生 Desk 承载动态业务页面和基础管理。
- `dsherp` 自定义 App 提供 Agent、构建和发布页面。
- 自有交互页面使用 React + Ant Design，通过 Frappe 扩展入口加载；不替换整个 Desk，不以 iframe 作为默认集成方式。
- 中文术语、导航命名、日期格式和字段布局统一适配；通过扩展资源实现，不 fork Frappe/ERPNext 核心。
- 不引入另一套通用页面编辑器；首版以对话生成、结构化编辑和原生预览为主。

### 2. 业务逻辑分层

| 需求 | 实现方式 |
|---|---|
| 字段、关联、子表、列表和表单 | 原生 DocType 与定制配置 |
| 角色权限、条件审批、通知 | 原生权限、Workflow 和相关配置 |
| 库存、账务、提交、取消等已有业务 | 调用 ERPNext 业务方法，不重新实现 |
| 特殊计算、复杂校验、跨对象业务动作 | Agent 生成自定义 App 代码与行为测试 |
| 外部系统集成 | 不作为首版默认能力，按明确业务需求另行规划 |

不把原生 `Server Script` 直接开放为多租户任意代码入口。v15 默认禁用它有共享环境安全方面的原因；受限 Python 也不能替代进程和租户隔离。[官方说明](https://docs.frappe.io/framework/user/en/desk/scripting/server-script)

### 3. 两类 Agent 职责分离

- **业务 Agent**：使用当前企业、当前用户的权限操作已发布应用，不能修改权限、结构或部署代码。
- **构建 Agent**：在隔离构建环境中生成配置、代码、测试和迁移方案，不持有生产开通凭证。
- **发布服务**：核验发布者、版本和确认内容，安装已确认的制品；模型不能直接选择生产目标或调用任意部署命令。

构建产物是一个有版本的应用变更包，包含配置差异、必要代码、测试、迁移说明及页面预览，不另建一套独立于 Frappe 的业务数据定义。

### 4. 发布流程

```text
描述需求
→ 检查现有应用与数据结构
→ 形成变更方案
→ 生成配置、必要代码和测试
→ 在隔离环境执行并预览
→ 展示页面、规则、权限及数据影响
→ 管理员确认具体版本
→ 发布服务执行
→ 回读验证并显示结果
```

- 发布确认与普通业务单据确认分开。
- 修改候选内容后，原发布确认失效。
- 发布前重新检查目标版本和权限，避免覆盖并行修改。
- 超时或结果不明时先查实际状态，不盲目重复部署或迁移。
- 展示失败步骤和已经完成的变更，不承诺跨步骤自动原子回滚。

### 5. 完整结构修改与运行隔离

- 先支持自定义业务对象的完整结构变更；对 ERPNext 标准对象使用官方扩展机制，不删除核心必需字段或破坏业务不变量。
- 删除和类型转换必须列出受影响数据、关联、规则及页面，在隔离副本试迁移。
- 发布前准备并验证必要备份；无法安全转换时停止并展示冲突数据。
- 恢复操作需考虑发布后新增数据，不自动用旧备份覆盖现有业务。
- 生成代码的构建环境与生产运行环境分离；不同租户的代码运行环境不得共享可访问其他租户数据或凭证的进程。
- 原生代码运行仍有风险，测试通过不等于安全证明；限制文件挂载、网络、凭证、资源与发布权限。

当前单站点验证环境不被描述为已经具备这些能力。新增环境必须先核对资源，超过既有授权时另行申请。

## 四、前后端接口与权限模型

接口按前端流程逐步实现，不提前生成大量空接口。

| 接口领域 | 最小职责 |
|---|---|
| 身份与企业上下文 | 当前身份、可进入企业、当前企业能力和角色 |
| 应用与导航 | 当前用户可见的已发布应用和页面入口 |
| Agent 任务 | 创建任务、补充输入、读取进度与实际结果 |
| 构建变更 | 需求、候选版本、配置及代码差异、预览结果 |
| 发布确认 | 确认具体版本及影响，读取发布和恢复状态 |
| 业务访问 | 复用 Frappe API 与明确业务方法，保留实际操作者 |

共同约束：

- 服务端验证企业成员关系、任务归属和发布权限。
- 前端不接触 ERP API 密钥、数据库凭证或部署凭证。
- 企业角色沿用 Frappe；新增的构建、发布能力通过明确角色与权限扩展，不复制一套 ERP 业务权限表。
- 页面、按钮和 Agent 工具使用一致的服务端权限依据。
- 切换企业时清理旧企业页面状态、查询缓存和事件订阅。
- 业务权限、应用发布权限、平台运维权限分别授予，互不默认包含。

## 五、实施顺序与验收

### 阶段 1：原生页面与中文体验验证

先让用户看到真实界面。

- 在独立测试环境补齐原生 Desk 所需服务。
- 展示中文 Workspace、物料列表、单据表单和角色管理页面。
- 实测中文搜索、字段布局、明细录入、日期数字显示和权限差异。
- 确定保留的原生交互及必要扩展，不先重做全站样式。

**交付：可访问的原生样板及浏览器验收结果。**

### 阶段 2：前端完整流程原型

- 实现企业工作端、构建空间和平台管理端的必要页面。
- 使用明确标注的合成数据，完成“提出需求—预览—发布确认—打开业务页面”交互。
- 提供角色切换演示，展示无权访问、发布失败、迁移冲突和部分成功状态。
- 未接入的操作明确标为演示，不伪造真实发布成功。

**交付：用户可操作并评审的前端原型；后端接口按已确认流程定义。**

### 阶段 3：身份与真实业务只读接入

- 接入真实身份、企业上下文和角色能力。
- 将已验证的 DSH→MCP→ERP 只读链接入页面。
- 补齐第二个隔离企业的验证，检查跨企业链接、缓存和任务访问。
- 替换对应演示实现，保留有效回归测试。

**交付：按真实身份查询 ERP 的企业工作端。**

### 阶段 4：原生配置生成与发布

- 生成自定义 DocType、字段、关联、权限、Workspace 和原生 Workflow。
- 在隔离预览环境运行，管理员确认后发布到目标测试企业。
- 完成“应用生成后可录入、查询和按角色处理业务”的闭环。
- 先覆盖新增及非破坏变更，作为后续完整结构修改的基础，不宣称全部需求完成。

**交付：第一个真实生成并可使用的业务应用。**

### 阶段 5：自定义逻辑与完整结构修改

- Agent 按 TDD 生成自定义 App 代码：先行为测试失败，再实现并验证。
- 完成代码构建、隔离运行、管理员确认及版本发布。
- 接入字段删除、类型转换、数据迁移、影响预览及恢复流程。
- 用设备维修场景验证条件审批、费用计算、非法状态拒绝和结构变更；现有设备对象优先复用。

**交付：同时包含页面、数据结构和真实自定义逻辑的应用生成闭环。**

### 阶段 6：制造业务验证与收敛

- 将构建和运行能力应用到原设计中的销售、采购、自制、委外及库存业务链。
- 明确复用 ERPNext 方法与新增逻辑的分界。
- 删除被真实实现替代的演示代码和临时产物。
- 分类提交，不自动推送，不添加额外 CI 或门禁。

**交付：真实制造场景验收及下一轮明确缺口。**

### 必须覆盖的测试场景

- 角色与企业不同，页面、记录、字段和动作权限均正确；直接请求不能绕过。
- Agent 生成的页面引用真实存在的对象和字段。
- 业务校验在服务端执行，跳过前端仍不能保存非法数据。
- 发布内容变化、权限撤销或目标版本变化后，旧确认不能继续使用。
- 数据迁移失败、部署超时和部分成功能够如实展示并核实状态。
- 备份恢复与应用版本回退分别验证，不互相替代。
- 生成代码不能取得其他租户或控制面的凭证。
- 原生页面扩展不影响既有 ERP 功能。

每阶段分别报告：**页面可用性、自动化测试、真实 Agent 调用、真实 ERP 操作、发布状态及尚未完成的能力**。当前规划不等于这些功能已经实现，也不包含生产环境变更授权。
