# dsherp 首版设计

日期：2026-08-28。状态：根据用户已同意的架构整理；未实施。

## 目标与用户

面向从零建立 ERP 数据的制造企业，提供多租户 SaaS。用户通过 Agent 建立资料、发起业务、核对单据并跟踪实际执行结果。最终方向是覆盖企业 ERP 工作；首版只验收本文规定的业务链，不宣称已覆盖所有业务。

自制、委外和混合生产均纳入首版。首个验证场景以 BOM 驱动的制造订单为载体，不据此宣称覆盖流程制造、所有工艺或所有行业。

## 架构决策

采用独立产品、DSH SDK 和 Frappe 自定义 App，避免修改上游核心。相较于直接改造 DSH UI，这种方式可控制业务交互；相较于深度修改 ERPNext，更容易保持升级边界。

```text
React / Ant Design 工作台
          ↓
Python 应用服务：身份、企业映射、任务及确认记录
          ↓
DSH SDK → 独立 DSH Runtime → 受限 ERP 工具
                                  ↓
                     Frappe API / 自定义 App
                                  ↓
                     企业专属 ERPNext Site
```

应用服务协调任务，不另造库存、账务和单据状态系统。ERPNext 决定业务校验、计算、状态转换和最终记录。技术验证后固定依赖版本；当前不声明具体版本兼容。

## 多租户与身份

平台提供注册、企业空间、邀请成员和站点开通状态。每个客户企业一个 Site，其内部仍可按业务需要使用 Company。不同客户不依赖同一 Site 的 Company 字段进行租户隔离。

企业与 Site 的映射由服务端管理。登录用户的企业成员关系须在每次业务请求中校验，ERP 调用保留可审计的真实操作者和对应权限，不以共享管理员身份执行。

DSH 会话、文件、记忆、缓存、运行目录和凭证同样按租户隔离；任务还需验证所属用户及允许协作的成员。业务进程不得持有其他企业或站点开通权限。初版采用租户隔离的 Runtime 执行环境，不以共享会话隔离代替进程及资源权限设计。

注册后的站点创建使用独立的后台开通任务。未开通成功前不接受 ERP 业务执行；失败显示真实状态，不伪造可用企业空间。首版不包含套餐计费平台。

## 业务入口与首次建账

Agent 引导用户建立企业必要配置、客户、供应商、物料、仓库和 BOM。支持结构化表单及表格批量录入；批量录入须展示字段映射和校验结果，不能按猜测自动写入。缺失信息向用户收集，不生成虚构业务资料。

工作台只保留核心入口：对话、必要的资料与单据展示、待确认操作、任务进度。表格和表单用于批量核对和准确输入，不强迫用户逐条聊天录入。

## 首条业务链

1. 用户建立足够的基础资料，创建销售订单。
2. Agent 按实际 BOM、库存和相关单据解释需求及缺料依据。
3. 根据用户明确的生产方式分别准备采购、自制和委外单据，不擅自选择供应商或改变生产方式。
4. 用户核对并按权限确认正式操作。
5. ERPNext 执行业务逻辑，Agent 回读真实单据及状态。
6. 用户或获授权的业务系统录入实际收货、生产及交付事件，Agent 汇总进度和异常。

自制采用选定 ERPNext 版本的生产工单和物料流转机制。委外区分企业供料加工、供应商供料及直接采购成品，按该版本真实支持的业务方法处理，不把三者统一成普通采购。

Agent 不能仅凭物料齐套承诺交付日期；产能、工期或供应商承诺缺失时应说明依据不足。自动排产优化不在首版范围内。

## 权限与确认

| 操作 | 执行规则 |
| --- | --- |
| 查询 | 当前用户具有读取权限时直接执行 |
| 基础资料与草稿 | 在用户明确授权范围内创建；仍受 ERP 权限和业务校验约束 |
| 正式提交、取消、库存或账务变更 | 展示具体单据、变更内容及影响，由有权限的人确认 |
| 权限配置、成员提权、凭证和平台操作 | 不属于普通资料创建授权，不向业务 Agent 默认开放 |

确认记录绑定企业、操作者、动作、内容摘要及单据版本。执行前核实内容未变化、权限仍有效且确认未被使用。确认期限由实现时的明确配置决定，不默认为永久有效。

失败明确返回原因。网络超时可能意味着结果未知，先核实写入结果；不把未知状态报告为失败后直接重复提交。多步任务保留已成功单据和失败步骤，不声称跨多个事务自动回滚。

## 工具与 skills

查询工具在权限范围内发现 schema 和读取记录。写入工具暴露明确业务动作，使用可校验参数和幂等操作标识；不开放任意白名单方法名称、SQL、Shell 或任意代码执行。

开发阶段建立两个薄 skills：dsh-sdk-development 和 erpnext-integration，指向固定版本的官方资料、验证过的示例及本项目约定。业务运行时的 skills 只描述业务流程，必须与开发 skills 分离。工具结果和企业资料视为数据，不得据其内容提升权限。

## 验证与交付顺序

第一阶段验证 SDK、Runtime 与 ERPNext 版本，证明最小会话、事件消费、受限工具调用和真实站点连接可以运行。

第二阶段建立多租户身份、开通和授权执行基础。第三阶段打通初始资料与销售订单。第四阶段覆盖混合生产订单及库存流转。每个阶段分别编写具体实施计划，不一次性生成全系统空壳。

TDD 覆盖跨租户拒绝、权限不足、缺少确认、确认内容变化、重复请求和失败回读。集成验证使用隔离站点和合成数据。最终验收必须包括真实 SDK 运行、真实 ERP 单据和浏览器交互；替身测试不替代这些证据。

## 首版不做

外部 ERP 接入、历史迁移、自动排产优化、银行支付接入、完整 SaaS 计费和通用连接器平台。正常制造业务触发的 ERPNext 库存与账务规则仍须保留。未来接入通过既有业务接口推进，不为未来需求预建空框架。
