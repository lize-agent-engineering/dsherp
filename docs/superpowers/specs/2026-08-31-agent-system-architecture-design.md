# dsherp Agent 体系架构设计

日期：2026-08-31。状态：方向性架构 spec，经四轮方案讨论后用户确认全部决策点；实施须另行制定分项计划并遵循既有 TDD、HITL 与验证证据约定。本文定义 Agent 产品层的概念模型、对象与边界，不改变已验证执行底座的任何不变量。

## 背景与定位

[2026-08-29 上下文 Agent 计划](../plans/2026-08-29-context-agent-sidebar.md)已交付可信执行底座：按消息一次性受限容器运行、受限工具 + 固定版本校验摘要 skill、统一提案-确认（HITL）协议、页面快照、来源账本、模型调用预算与压缩防护。本 spec 在该底座之上定义 Agent 产品层：多助手模型、引导体系、角色治理与能力扩展轴。

总原则：任何新能力一律作为"提案类型 + 执行器 + 场景知识"接入既有底座，不绕过；答不出这三问的能力不做。

## 三轴能力模型

任何一项 agent 能力定位为三元组（业务领域 × 能力层级 × 作用范围）：

- **业务领域（domain）**：销售、采购、生产（含委外）、仓储/库存、财务、质量等，对应 ERPNext 模块与企业部门划分。
- **能力层级（tier）**：只读查询 → 业务写入 → 结构写入。原实现中的 query/operation/configuration 自此改称能力层级；层级决定工具集与确认强度。代码标识符（如 `DSHERP_DOMAIN`）不随本 spec 立即更名。
- **作用范围（scope）**：系统级（租户站点）→ 公司级（站点内 Company）→ 部门级（角色）→ 个人级（用户）。多 Company 首期合并处理（单法人客户下站点级≈公司级），但策略表与 Profile 数据结构预留 Company 维度，避免多法人客户出现时返工。

横切与排除：

- **产品级**（dsherp 产品自身的使用知识）作为横切知识层进入 agent 体系，见引导体系。
- **平台运维级**（开站、配额、租户管理，持控制面凭证）永不进入 agent 体系；控制面凭证不得进入业务 Agent 维持既有约定。

## Agent Profile（服务端一等对象）

助手 = 命名的运行装配配置。底座按消息临时装配运行，故"多个助手"不是多进程、多模型或编排框架，而是多份 Profile 装配同一底座。字段草案：

- `name` / `persona`：名称与人设（如"销售助手"）。
- `domains`：覆盖的业务领域，圈定工具可及的 DocType 范围与默认关注单据。
- `tiers`：开放的能力层级。
- `skills`：装载的 skill 清单（固定版本 + 摘要，沿用 business-skills 管线；loader 需支持多 skill 装载）。
- `served_roles`：服务的 ERP 角色列表，用于推导可见性。
- 上下文策略与预算档位。
- 确认路由提示：该助手提案默认路由到的角色。

Profile 只做减法：执行权限永远是当前映射用户 ERP 权限的交集，服务端逐次复查。Profile 与全部治理配置为业务 Site 原生 DocType，由 System Manager 以原生权限管理；agent 对其零工具访问、零提案能力。

## 助手清单与优先级

| 范围 | 助手 | 层级 | 说明 |
|---|---|---|---|
| 公司级 | 启用向导助手 | 只读 + 业务写 | 第一优先。新租户默认对话对象；建账完成前对全员可见（角色体系未建，无从推导），完成后按正常规则收敛。进度以 ERP 事实推导为主（如"已有至少一个客户"是查询不是标志位），仅用户显式选择落库。应用需求成型后交接应用构建助手，交接物为清单与需求草稿，非 agent 间对话 |
| 公司级 | 经营总览助手 | 只读 | 跨领域查询与解释的唯一出口；写入动作回到对应部门助手，保证确认路由干净 |
| 部门级 | 销售 / 采购 / 生产 / 仓储 / 财务助手 | 只读 + 业务写 | 按部门（ERPNext 模块）切 Profile；跨助手流程知识作为场景 skill；财务助手首期只开只读（账务写入风险最高，会计分录多由业务单据提交自动生成） |
| 系统级 | 应用构建助手 | 结构写 | 既有 configuration 链路（包 → 隔离预览 → 签名回执 → 独立发布）。生成应用附声明式验收断言，预览站执行器运行、结果入签名回执；不生成可执行代码 |

部门助手推进顺序跟随首条业务链：销售 → 生产（含委外）→ 采购 → 仓储 → 财务（只读）。

呈现按人聚合：界面显示"你的助手"= 用户角色命中的 Profile 集合；一人多角的小厂用户可聚合呈现，只有多角色用户才感知多个助手存在。

## 交互与路由

- **双入口维持**：页面侧栏 = 现场协作（页面快照绑定当前对象）；工作台 `/app/dsherp-agent` = 任务中枢（对话、待确认、执行记录、应用配置）。
- **分诊路由**：运行前由服务端做轻量意图分诊（规则优先、模型兜底）选择 Profile 与层级，明示"本轮由 X 助手处理"，用户可纠正。取代用户手选"任务领域"下拉框。分诊是顺序前置步骤，不构成多 Agent 并发框架。
- **确认收件箱**：提案者与确认者分离进入下一阶段。提案携带所需单据权限；收件箱按该权限过滤路由。确认权完全复用 ERP 单据原生权限，不建新角色体系。
- **用户心智只讲三个动词**：问（直接答）、做（要确认）、改应用（要预览 + 发布）。"提案""运行""领域"等系统词只留在审计记录。

## 工具扩展：通用提案工具 + DocType 策略表

从逐 DocType 硬编码工具（现仅 Item / Customer / Sales Order）转向 schema 驱动的通用提案工具：

- 服务端维护 **DocType 策略表**：每 DocType 声明各能力层级允许的动作（读 / 草稿 / 提交等），与首版设计权限表对应；预留 Company 维度。
- Profile 的 domains 圈定可及 DocType 子集；用户 ERP 权限仍为最终边界。
- 配置发布的新应用通过运行时 schema 发现（`erp_read_schema` 既有）+ 发布时生成的应用清单进入助手认知，不靠人工改 skill 追赶。

## 引导体系

"引导"拆为三件事，三个归宿：

1. **产品操作引导**（这是什么、怎么用）：product-guide skill 横切装载进所有 Profile + 静态 UX（首次导览、空状态、图解）。工程纪律：改交互的提交必须同步更新 product-guide skill，防止产品知识漂移；摘要固定沿用既有管线。页面快照使引导情境化（"你现在在物料列表页，下一步…"）。
2. **业务构建引导**（从零到可运营）：启用向导助手，见清单。
3. **日常流程引导**（下一步该做什么）：部门助手场景 skill 内置。

平台站点阶段（注册 → 邀请成员 → 等待开通）：静态清单式引导 + 真实开通状态展示，无 agent；引导助手从用户首次进入业务站点开始接管。访客/售前体验沙箱（`dsherp-studio` Demo 为候选）远期挂账，不预建。

## 角色与治理

agent 与角色的关系拆为三个独立问题：

- **执行权限（安全边界，既有不变量）**：agent 以映射后的真实业务用户执行，每次工具调用与确认由服务端按该用户 ERP 权限复查。共享 Administrator 账号不使用 agent。角色对 agent 的治理单向：角色决定 agent 能做什么；权限配置、成员提权不向 agent 开放，含提案。
- **可见性（体验匹配）**：`served_roles` 推导 + 管理员按（用户 × Profile）粒度覆盖表加白/拉黑。
- **准入（成本治理）**：租户总开关 + 层级差异化——只读层级默认全员开放（产品价值第一触点，零写入）；业务写层级随可见性；结构写按配置类角色收紧——+ 用户预算档位。

用量与预算：用量报表基于既有 DS Model Run 记录（已按用户/会话/领域持久化）聚合展示；单次运行预算沿用 `reserve_model_call`；按用户/按月累计额度后置。

## 协调与编排原则

- **多助手零编排框架**：跨部门协作经由 ERP 单据状态流转完成（单据即协调总线），无 agent-to-agent 协议，审计天然完整。
- 将来需要并行（如配置生成 + 校验），编排放在服务端确定性代码，模型不掌握调度权。
- 接力提醒 / 进度哨兵（事件或定时触发的只读异常汇总）为后续独立方案：涉及非用户触发的模型费用与触发授权模型，本 spec 不含。

## 明确不做

- 多 Agent 编排框架、模型驱动的 agent-spawn-agent。
- 自由文本企业长期记忆；偏好尽量从 ERP 数据推导。
- 配置 agent 生成可执行代码；以声明式验收断言替代。
- agent 进入平台站点；平台运维级 agent。
- 未认证访客 agent。

## 实施顺序（高层）

1. Agent Profile 对象 + 分诊路由 +（用户 × Profile）治理配置与准入开关。
2. 启用向导助手（product-guide skill 同批建立，多 skill 装载随此落地）。
3. DocType 策略表 + 通用提案工具（承接制造链 DocType 扩展）。
4. 经营总览助手；部门助手按销售 → 生产 → 采购 → 仓储 → 财务（只读）推进。
5. 确认收件箱（提案者/确认者分离）。

每步另行制定实施计划，遵循既有 TDD、真实 Runtime/模型/ERP/UI 分层验证与证据约定；本 spec 不构成任何一步的实施计划。
