# 备份切片设计审阅

审阅基线：`plan4/backup` / `faa4d38`，设计稿 `docs/superpowers/specs/2026-09-06-backup-offsite-design.md`。PR #7 已合入 main `30cf6fb`，本轮没有实施备份代码、改动部署或连接对象存储。

结论：**采纳方案 A 的架构方向，按下列意见修订设计后进入实施计划。** 不需要再做多轮大规模勘察，也不需要新增通用备份平台。

## 六项裁决建议

| 项 | 建议 |
|---|---|
| 1 宿主 timer 驱动 | 同意。平台与租户站复用一条生成链路；同步修改上位设计。调度周期必须给 RPO 24h 留出运行及补救余量，建议每 12h 生成并同步，而非每日一次加随机延迟后到 26h 才告警。 |
| 2 一次性 restic compose 服务 | 同意。固定版本及镜像 digest，服务职责按实际行为验证。移除阻碍一次性服务的脆弱测试；不要改成“常驻13+一次性1”的新数量门禁，也不要逐行锁住 unit 文本。 |
| 3 每日全站恢复 | 改为每周完整恢复验证，首次启用、应用版本或备份格式变化后额外执行；8日未验证告警与周周期一致。日常执行备份完整性与同步检查。完整演练放在隔离环境，避免每天在业务栈复制全部租户数据。 |
| 4 本机第二项目自证 | 同意。独立数据库、卷、网络与运行目录，可使用私有 CA 并实际验证证书。它证明工具链，不能证明物理异机容灾、真实异地副本或正式 RTO。 |
| 5 本地三套、归档不出机 | 部分同意。本地三套为默认，保护最后一套已验证可恢复副本；日常同步不必扫描全部归档卷，但租户下线的最后备份、发布回滚所依赖的备份应有事件触发的异地保存，不能一概排除。 |
| 6 状态文件→worker→告警 | 采用作为统一展示路径，保留逐站、逐阶段的最后成功时间、当前尝试与错误；同时复用 systemd 的失败通知或外部监控补足 worker 停止时的盲区，不建立第二套指标平台。 |

## 实施前必须修订的行为契约

### 1. 备份文件与核验快照必须对应同一份业务状态

设计 §4.1 先 backup，随后读取仍在运行的源站作为 snapshot。期间订单、库存或后台作业发生合法写入，恢复出的正确备份也会与这个稍后的快照不一致。仅检查 maintenance_mode、只给备份命令加 flock，都不能排除它与 release/rollback 或业务写入交错。

本次读取固定 Frappe 16.31.0 备份实现：先 take_dump，再 copy_site_config，再分别打包 public/private files；它不会把后续的任意站点快照纳入同一事务。

建议复用现有维护机制和协调锁：备份与 release/rollback/下线互斥；暂停新写入并等待在途工作退出，在同一稳定窗口生成四件套和 G2 快照。纯备份成功或失败后恢复原站点标志；恢复失败则保持恢复目标隔离。若不能接受暂停写入，应单独设计在线一致性方案，不能默认为两个独立读取天然一致。

### 2. 数据和密钥必须绑定同一个备份集

§4.5 对两个仓库分别 restore latest，会在“数据上传成功、密钥上传失败”时取到不同批次。以不可混淆的 backup_set_id 绑定站点、数据快照 ID、密钥快照 ID、制品版本和校验值；两部分都成功且回读一致后才标记该备份集为 complete。恢复选择最新的完整配对，不能独立取两个 latest。

半成功上传可保留为 pending；后续运行先核实已有结果，只补缺失的一侧。同步成功时间必须代表可恢复的完整配对，而非其中一个仓库刚写入。

### 3. 修正 restic 保留分组

§4.2 同时设置 site 和唯一 stamp 标签，再用 `forget --group-by tags`，会让每次备份各成一组；每组只有一份，保留规则无法淘汰旧组。restic 官方明确按选定属性分组后，逐组应用策略。[restic 保留文档](https://restic.readthedocs.io/en/stable/060_forget.html)

保留策略应按稳定的站点维度工作：例如先按 site 标签筛选，再禁用组内按 stamp/动态路径分组；具体参数以实施时固定的版本确认。stamp/set_id 可以继续用于恢复定位，不能成为保留分组键。数据与密钥仓库的清理还须保护完整配对及最后一套有效副本。

`keep-monthly 3` 不是“任何副本最多存在三个月”的保证；保留按有快照的周期计算，清理未运行时也不会自动到期消失。删除边界文案应如实说明保留规则与执行条件。

### 4. RPO 与失败可见性不能从24h放宽为26h

每日一次、随机延迟15分钟、任务允许运行6小时、失败等次日，会在正常调度抖动下超过24h；失败一次则可能接近48h。建议每12h生成同步，按备份代表的数据时点计算年龄，并在24h之前预警，达到24h即标记目标未满足。新站没有首份完整异地备份时也必须显示未达标。

状态文件在开始及各阶段完成/失败时更新，保留 last_success 与 last_attempt，不能失败后抹掉上次成功事实。任务失联、超时、worker 停止不能让五分钟可见性承诺失效；监控范围应从平台与租户清单得到，而不是只信旧状态文件里出现过的站。

### 5. 恢复环境从创建起隔离，清理必须真实完成

恢复副本不得进入业务入口、生产 worker 领取、邮件/Webhook 或其他外部副作用链。复用已有隔离预览经验，先建立隔离，再恢复数据和解密密钥，失败不得放开。按备份记录的制品版本恢复并核验；升级作为后续显式 G2 动作，不要以“tag不同就migrate”混合恢复与升级。

`bench drop-site --no-backup` 会把整个站目录移入 archived/sites，不是删除物理副本。本项目已为该目录挂持久卷；周期性演练若只 drop，会持续累积完整数据及密钥副本。清理只针对本次演练确切拥有的站、目录和归档；失败诊断资料有明确保留期限，不能遍历清空整个归档卷。

### 6. 密钥分离和口令日志需覆盖本片新增路径

两仓库分别使用口令是正确方向；默认同一对象存储凭据、同一可读挂载和同一 Unix 用户，仅靠两个目录名及 chmod 不构成权限隔离。应明确数据-only访问者不能取得密钥仓库的解密凭据，默认采用按仓库限定的访问身份；恢复操作在授权范围内才取得两侧材料。

Frappe 原目录中的 site_config 副本也要纳入权限和清理说明，不能只隔离复制后的那一份，却继续宣称“永不同目录同权限”。历史 bench.log 的清理可以另排，但本片新增的周期性 new-site/restore 不应继续新增明文 root 口令；这是新链路的凭据风险，不应整体推迟到短期凭据切片。

### 7. 下线后的最后状态不能只留在本机

日常备份并不包含最后一次日常备份之后、下线之前的全部变化。下线后站点会退出日常遍历范围，若最终归档不出机，主机损毁会失去这段最后状态。发布/下线的备份可复用同一备份集协议事件式上传，无需同步整个归档目录。其保留与删除口径应与审计保留决策一致。

## 最小实施与验证顺序

1. 先实现备份集协议、稳定窗口、生成和状态记录，覆盖并发写入及发布互斥。
2. 接入双仓库同步和配对，覆盖单边成功、存储失联、过期告警以及真实保留淘汰。
3. 实现隔离恢复、密钥解密核验及确切清理；以第二个本地栈跑完整回路。
4. 接入 timer 和已存在的可见性链路，验证 worker 停止时仍能发现备份故障。

测试以这些真实行为为准；不固定服务数、DocType数或源码写法。`restic check` 的结构检查不能替代实际数据读取和恢复，官方另提供 `--read-data`/分片读取用于数据检查。[restic 仓库检查文档](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)

本审阅未执行备份、连接对象存储、创建恢复站点或修改既有设计稿。具体版本/digest与真实容量数据由实施时核实，G3正式验收继续独立保留。
