## 总体判断

计划 4 的主体实现已经交付，核心防护有实质提升：备份从单份转储发展为可配对、可核对的备份集；升级/恢复能比较真实数据；审计、用户删除和凭据生命周期都有服务端行为约束。之前的审查和修复有价值，既有收口结论不应因每个普通改进项反复重开。

不能用一个“完成百分比”同时概括代码、功能和生产验收；本复盘按下面的实际结果判断。

## 当前可复现的 bug

### B1 · P1：backup --sync 同步失败仍以退出码 0 结束

位置：[backup.py](../../dsherp/backup.py)，314–315 行；[admin.py](../../dsherp/admin.py)，2024–2029 行；[定时单元](../../infra/render_worker_units.py)，135、144 行。

本地备份成功后，`backup()` 将 `backup_sync()` 的结果放入 `report['sync']`，没有将同步失败合并到顶层 `ok`。CLI 只根据顶层 `ok` 决定退出码。systemd 的命令恰好是 `backup --sync`，因此对象存储不可达时，本应兜底的 `OnFailure` 不会因该命令失败而触发。

独立复现调用真实 `backup → backup_sync → admin.main`，仅替换 bench、Docker 及仓库可达性 I/O：

```json
{"exit":0,"backup_ok":true,"sync_ok":false}
```

worker 正常时仍可能从状态文件报告同步失败，所以不能说“系统完全不告警”；问题是 worker 停止时依赖的旁路通知链失效。修复应汇总整个命令的结果，并直接验证 `backup --sync` 的失败退出码与定时单元衔接。现有测试分别验证了独立 `backup-sync` 和单元命令文字，漏掉了组合。

### B2 · P1：本机状态丢失后，冷恢复会跳过错误构建检查

位置：[backup.py](../../dsherp/backup.py)，676–682、594–595 行；[backup_status.py](../../dsherp/backup_status.py)，`record_set`；[restore_drill.py](../../dsherp/restore_drill.py)，372–395 行。

灾后没有本机 `status.json` 时，`backup-sync` 会重新发现远端集合。发现阶段只保存站点、集合 ID、种类、时间；虽然随后读取并验证了远端清单，却没有将清单里的 `image_id/image_tag` 回填到重建状态。`restore-site` 又只在本机状态含 `image_id` 时检查运行镜像，取回真实 `set.json` 后没有再次核对。

独立复现的连续路径：生成并同步一套备份 → 清空本机状态 → 从原远端仓库重新发现 → 使用不同镜像 ID 冷恢复。外部 I/O 使用现有替身，实际编排函数与清单配对逻辑均运行：

```json
{"sync_ok":true,"adopted_image_id":null,"adopted_image_tag":null,
 "restore_clean":true,"maintenance":"released"}
```

该路径正对应主机丢失后的恢复，不是任意篡改配置才能触发的边角场景。应从已核验的远端清单恢复完整身份，并让恢复前检查始终以已核验清单为依据；缺少身份就拒绝，不能跳过。

这是编排层可确定复现的缺陷，本轮没有真的向错误构建恢复数据库。

### B3 · P2：部分失败场景仍把用量报告标为完整

位置：[model-guard.cjs](../../runtime/model-guard.cjs)，31–49 行；[usage.py](../../dsherp/usage.py)，66、155–173 行；[admin.usage_report](../../dsherp/admin.py)，1279–1297 行。

两种场景已独立复现：

1. 实际 guard 流程收到部分文本后超时，事件为 `model_call_reserved → model_error`，没有 `model_response`。汇总只处理后者，结果为 model_calls=1、token=0、unknown_calls=0、complete=true。这里实际消耗未知，不能证明是零。
2. 两个站点均不可达，`unreachable` 正确列出两站，但各站与总计仍 complete=true。CLI 对不可达情况已有非零退出码，问题在 JSON 完整性字段与实际缺失数据矛盾。

修复应覆盖“调用已开始但没有最终 usage”和“数据源缺失”，保留已知用量并把未知范围传到汇总。此项影响计量与运维判断，不是 ERP 业务单据损坏，也不需要引入完整计费平台。

## 软件质量工程问题

### Q1 · 当前测试缺陷：验证了错误的对象

[test_restore_drill.py](../../tests/test_restore_drill.py)，231–237 行，传入演练的是一个 `DrillBench`，随后却新建另一个对象并断言其 `scripts` 为空。这条断言天然成立，无法证明错误镜像场景没有先执行建站。

本轮用内存中的反例令实际传入的对象记录 `_new_site`，再返回镜像拒绝，原测试仍通过。前面的结果断言仍有价值，应保留；修正为检查实际传入对象即可，无需增加新的门禁体系。

### Q2 · 局部测试较强，完整操作链覆盖不足

本轮相关现有测试 **67 passed**，上面组合反例仍成立。问题不在测试数量，而在各测试验证的关系：

- 同步失败、CLI 退出码、systemd 配置分别通过，没有验证同一次 `backup --sync` 的端到端失败传播。
- 远端重新发现、镜像拒绝分别通过，没有覆盖“状态完全丢失后再发现并恢复”。
- `provision` 或 `ensure_enterprise` 被替换时，组合测试看得到调用次序，却看不到被替换函数内部的真实状态转换。第三轮状态回归就是这种盲区的实例。

计划 4 的强项也应保留：真实双事务绑定唯一性、递增版本、运行授权缓存与撤权、真实站点删除/改写拒绝，以及已有备份/恢复形状验证。这些不是摆设，已经降低了实际风险。

### Q3 · 字符串断言、共享夹具和清理机制形成工程债

- [test_business_credentials.py](../../tests/test_business_credentials.py)、[test_run_grants.py](../../tests/test_run_grants.py) 的部分用例通过函数名、源码语句或调用次数证明行为。应逐步替换这类断言；保留有实际价值的 schema/迁移契约检查，不能笼统删除所有静态检查。
- [集成 conftest](../../tests/integration/conftest.py)，55–82 行，对 HTTP 错误、网络错误等统一返回 false 后自动重签凭据。它提高了可重复运行性，也可能把前序污染或环境故障修掉，使首个故障更难定位。应区分认证失效与服务不可达，并明确哪些测试拥有凭据轮换。
- 许多真实站测试将创建、断言、清理放在同一注入脚本里；进程被杀或中途失败时，尾部清理可能不执行。队列白名单保护是正确的，但长期需要登记式夹具清理和独立 finalizer。

FrappeTestCase、集成 finalizer 与通用 CI 已在[总体设计工作流 G](../superpowers/specs/2026-09-03-production-hardening-design.md)列入计划 5，应由下一计划承接，不作为计划 4 新增的整体阻断条件。

### Q4 · CI 尚未接线，不能用 main 上的空差异检查代表持续验证

仓库没有 `.github` workflow，GitHub 最近运行列表返回空。迁移检查脚本存在，但 [test_doctype_patch_guard.py](../../tests/test_doctype_patch_guard.py)，58–72 行以 merge-base(origin/main, HEAD) 为起点；在当前 main 上是空区间。这可以证明命令调用成功，不能证明某次发布迁移已被验证。

计划 5 接线时应明确 PR base/head 与上一发布 tag 的基线，接入现有检查与演练能力。无需为本复盘临时再建一套流程。

### Q5 · 当前状态、实现和原计划有几处尚未对齐

- **灾后发布状态**：设计要求成功恢复后写 `releases/current.json`，代码只写 verified 和恢复报告。本轮冷恢复替身成功后该文件仍不存在，下一次 release 将要求 `--from` 和旧清单。有安全的手工退路，列普通运维完整性修正即可。
- **skill 版本归因**：[context_runner.py](../../dsherp/context_runner.py)，95 行只给 runtime_started 发 session_id，没有 skill_versions。validation 的只读抽样中，58 条有模型调用的运行均无 skill_versions，5 条 runtime_started 事件也均缺此字段。至少这条元数据产出链尚未接通。provider_request_ids 在这 58 条运行中也为空，但是否可从固定 SDK 获得还需确认，不据此直接断言 provider 集成有 bug。
- **策略口径**：计划写“归档 90 天后清理”和“UTC 存储”；实际 `sessions.sweep` 按目录最后写入时间清理，Frappe 时间按站点时区解释后在月报转 UTC。应明确当前采用的口径并同步上位计划，避免以后按两种定义验收。
- **状态台账**：README 仍写“完成两片/backup 分支”，部分证据仍写凭据裁决待复核；后文又指向已完成的回应。应维护一个简短的当前状态表，历史记录继续保留。
- **可维护性**：admin.py 为 2134 行，包含 CLI、生命周期编排和动态生成的 Frappe Python 脚本。长期会妨碍行为测试与静态检查。计划 5 中优先提取确有测试困难的逻辑，避免整文件重构。

## 执行过程复盘

做得好的方面：优先复用 Frappe 和现有运行/保持机制；关键操作使用显式状态和数据库唯一约束；遇到真实站错误后修正契约，并记录未完成验收；功能提交和审查证据最终都入库，审计保留与个人删除的边界也得到明确裁决。

需要改进的方面：最初按功能切片和局部测试报告完成，跨命令的操作链证明偏晚；替身被当作边界时，容易遗漏内部状态转换。前几轮审查也在受控恢复的边缘状态上投入偏多、定级偏高。下一次应更早从用户/运维的完整链路出发，按影响与触发场景排序，减少“补一个点、再开一轮大审查”的往返。
