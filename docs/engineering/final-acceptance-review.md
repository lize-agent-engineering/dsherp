## 判定规则

台账的全部价值在这条规则上：**只有能指到「今天可重跑的一条命令」「一次真实的 CI run」或「一份带原始输出的演练记录行号」的判据才算成立。指不到就是无证据，不因为哪份文档写着「已验证」而放行。**

| 判定 | 口径 |
|---|---|
| **成立** | 能指到今天就能重跑的一条命令（给命令与它定义在哪个文件哪一行）、或一次 `conclusion=success` 且确实覆盖该判据的 CI run（给 run id）、或一份带**原始输出**的演练记录（给 文件:行号，那几行必须是真实输出而不是叙述） |
| **证据过期** | 证据存在，但它证明的是已经变过的代码路径、已经不存在的环境、或被后来的事故/变更推翻的读数 |
| **无证据** | 文档声称做到了，但指不到上面三种任何一种；只有叙述性文字 |
| **未闭合** | 本来就还没做，公开在等外部资源（主机 / 审计方 / 时间窗）或后续切片；机制建起来了但判据字面明确未达（覆盖面差一截、时间窗没走完）也归这一档，证据列写清差在哪 |

「是否阻断 G10」回答一个问题：这条不成立时，24 小时浸泡还能不能有意义地开始并通过。

## 台账怎么来的

按已裁决 #2 的口径，终验的审计方是**一个不给上下文的独立会话**。本文是在那之前由执行方先做的一轮自审，方法是三层：

1. **拆解与找证**：十道门各一个不共享上下文的代理，把判据拆到原子级，在 `tests/`、`infra/`、`dsherp/`、`.github/workflows/` 里找可重跑的东西，在 `docs/engineering/` 里找带原始输出的记录，用 `gh` 核实 CI run。
2. **对抗性核查**：每条判据再派一个代理，任务只有一个——**推翻它**：命令真的存在吗、run 真的绿且覆盖这条吗、那几行真的是原始输出还是叙述、是不是只在本机绿、证据日期与代码路径之间有没有变更。不确定时倾向推翻。初判 105 条里 41 条被推翻，其中 24 条是从「成立 / 证据过期」降到「未闭合」，2 条反向升到「成立」（核查者找到了初判没找到的测试）。
3. **完备性批评**：每道门再派一个代理逐字对照原文，找拆解时吞掉的分句。收进来 16 条，合计 121 条。
