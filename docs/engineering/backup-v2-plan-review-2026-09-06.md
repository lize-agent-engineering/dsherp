# 备份设计 v2 与实施计划审阅

基线：`plan4/backup` / `f5d067d`；设计提交 `7602585`。本轮审阅设计及计划中的代码草案，没有实施备份功能、修改部署、连接对象存储或操作业务数据。

结论：**架构方向和默认取值同意，当前实施计划暂不整体放行。** 计划中的若干代码草案与设计承诺不一致，先修订下面六组问题。执行方式建议由同一会话按任务顺序 TDD，四个阶段末各保留一次检查点；不需要每任务换代理或追加多轮大规模勘察。

## 默认值与执行节奏

- 02:00 / 14:00 可接受，明确使用 Asia/Shanghai；备份集时间戳及年龄计算仍统一 UTC。
- 20h 预警、24h 未达 RPO、13h 调度失联、8日未验证阈值可接受。
- 失败演练资料保留14日是上限，失败立即通知并处理，不是允许等14日再处理。
- `kind=retire` 不自动淘汰、两仓库使用不同存储身份可接受。
- 每任务跑相关行为测试，阶段末跑完整回归与该阶段真实链路。不要把所有真实验证推到 Task 16；实施计划开头“每任务跑全量”的要求可改为此节奏。
- 计划中的实现代码视为候选方案，不锁死等价实现、函数名称或源码布局。阶段验收围绕能完成的真实动作。

## 1. 稳定窗口仍没有成立

计划 Task 5 `backup_window`（875–900行）先写 hold 停止领取，再等待 `_site_flags().active == 0`。当前 `dsherp/admin.py:619–620` 的 active 包含 Queued，因此已有排队任务既不能被领取，又一直阻止备份，最终只会超时推迟。另一个方向也有遗漏：NeedsInput 仍持 capability 的运行尚未交还执行权，却不在该计数内。

应把“停止领取新任务”与“等待已有执行者退出”区分开：排队任务可冻结，等待的是实际在途执行者；需要处理 worker 已通过 hold 检查、claim 尚未返回的窗口。维护标志与 pause_scheduler 也不会自动终止已经开始的普通 HTTP 写入和后台作业，必须给出排空这些写入者的具体机制。

测试至少覆盖“Queued 存在但无执行者”“正在领取时建立保持”“已有 HTTP/后台写入尚未结束”。纯备份退出时恢复原标志；部分设置标志失败也要清理已经完成的动作。

## 2. complete 的实现退化成了“有两个快照 ID”

设计要求读回并核对 set.json/pair.json 后才 complete，但 Task 9 的 `upload_sets`（1641–1677行）只查标签取得 ID，1664行就由两个 ID 决定 complete，没有读取配对内容。已有本地 ID 时还会直接跳过该侧检查。`_remote_sets`（1684–1700行）也会仅凭两侧标签把未知集当 complete。

应在变为 complete 前读回精确快照的两份清单，核对 set_id、site、format、各件摘要及 set.json 摘要；使用完整快照 ID。记录过的远端副本需要先确认仍可用，不能仅凭本地缓存。配错或无法验证时保持 pending/failed，禁止把它作为 RPO 成功或下线前置。

恢复侧 `_verify_fetched`（2102–2118行）检查三件数据摘要，却没有验证已记录的 snapshot_sha256；密钥件自身也没有摘要绑定。协议应覆盖所有实际用于恢复与判定的材料，并给每项新增摘要写明准确输入、规范化、来源和诊断方式。

## 3. 恢复版本、凭据和环境接线与设计不一致

- Task 5 的 backup 调用没有传入实际 images，`backup_window`（902–905行）会把 image_id 写为空；Task 6 的 retire 示例（1075–1078行）也直接写空。备份必须记录实际可核验制品身份，不能让恢复时才发现缺依据。
- Task 11 在2154行先用当前 `resolved['image_tag']` 启动栈，取回后仅拒绝 tag 不同的备份；这不是按备份版本恢复。应先取回/核对元数据，按备份的版本与 ID 选择镜像；不同站点的完整备份属于不同版本时，明确分组恢复。
- `DrillStack._run` 会传临时 secrets_dir 和备份 tag，但 `bench()` 返回的 Bench 只替换命令构造，没有复用这段环境传递。冷启动所需的 bench 初始化、恢复凭据、私有 CA 及实际镜像核验要走真实接线验证，不能由假 Bench 默认成功代替。
- Task 12 建议把 root_password 临时写进生产共享 common_site_config.json。优先使用已核实的 stdin/进程内能力，避免把控制面 root 凭据放入服务全部租户的共享卷。只是不出现在 argv，并不等于没有新增凭据暴露。
- 恢复 fetch 服务都挂同一个可写 fetched 卷，会互相看见另一侧取回的内容；应分别挂数据与密钥卷，只让隔离恢复 backend 在授权范围内取得两侧材料。

## 4. 未配置仓库仍可以下线

设计 §4.1 及 §4.6、Task 6 的1080–1081行均保留 `if backup_repository` 后才上传的路径。仓库没有配置时会直接跳过“最终备份完整到达异地”，与已采纳的下线契约矛盾。

生产下线应在任何破坏性动作前要求双仓库可用、最终集完成配对确认。开发演练若需要本地模式，应显式区分，不能由“缺配置”隐式进入。阶段1的临时占位路径不能成为已交付的生产行为。

## 5. 失败通知与监控仍有伪成功/静默缩小范围

Task 13 的 notify_failure（2421–2434行）调用现有 Notifier.emit 后无条件返回 posted。现有 Notifier 会吞掉 HTTP 异常，并向 sink 报投递失败；该草案又把 sink 设为无操作。

本轮直接执行计划中的此函数，以不会发网络请求的故障客户端模拟投递：客户端抛 ConnectionError，函数仍返回 `webhook: posted`。应只有确认投递成功才报 posted，失败明确返回并保留 journal 证据。

Task 14 第2670行还规定租户清单读失败后回退到 worker profile。这会重新漏掉平台站或未进入 profile 的租户，违反“监控范围来自权威清单”的设计。应报清单不可用，不能缩小范围后计算健康。类似地，操作命令不能把损坏的状态文件静默初始化为空后执行保留删除，丢失“最后已验证副本”的保护依据。

## 6. 计划中的兼容性与测试约束需要整理

- Task 1 的 slug 保留站名中的连字符，但 SET_ID 的 slug 正则只接受 `[a-z0-9_]+`。本轮确认 `dsherp-validation.localhost` 产生的 ID 无法被计划中的解析器接受；应覆盖项目现有真实站名。
- Task 13 的日历表达式写成 `02:00,14:00:00`，把两个时间混在同一小时/分钟/秒表达式中。按 systemd 的小时列表语法，应写为 `OnCalendar=*-*-* 02,14:00:00 Asia/Shanghai`，并在 Linux 用 `systemd-analyze calendar` 核对下一次触发时间，不能靠正则锁住错误文本。本次依据官方语法核对，未在本机执行 systemd。[systemd 官方时间语法](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.time.xml)
- Task 10 的1785–1800行仍固定恢复服务集合、精确源码字符串和配置写法；Task 13 也大量逐行匹配 unit 文本。这与计划开头的“不锁数量/源码形状”矛盾。应验证网络隔离、挂载权限、调度和命令效果，复用解析器或真实工具，不要求某一种文本排版。
- `restore-site` 是 G3 的核心交付，Task 12 当前主要是流程描述和一个假流程测试。应补明确的冷启动恢复契约：目标站不存在/不可覆盖、元数据与制品先核对、凭据只在必要范围使用、恢复与最终主机配置完成后再核验可用、失败保持隔离。

## 四阶段检查点

1. **生成**：真实合成站点有稳定的一套四件备份及核验快照；并发写入不会造成错配，排队任务不会让备份永久推迟。
2. **异地**：真实双仓库上传、单边失败补齐、错配拒绝和保留淘汰；下线的破坏性步骤受完整配对约束。
3. **恢复**：按备份实际版本在独立栈恢复、解密和业务核验；只有异地材料的新栈也能恢复；成功清理与失败保留都有证据。
4. **调度与可见性**：12h/每周调度有效；worker 停止、通知失败、清单/状态损坏均如实可见。

这些修订都是已经采纳的设计契约的具体落实，不需要再扩展架构。默认取值本身无需再讨论；修订前不要把2717行代码草案当作已审定实现直接照抄。
