## 合并前需修复的六组问题

### R1 [P1] 迁移或恢复失败后仍解除维护

位置：`dsherp/admin.py:754–787,836–856`。

release 只有 migrate 自身抛 Fault 时设置 failed。迁移后快照读取、文件写入、patch 导入、声明校验或 compare 异常，finally 都会恢复原站点标志；compare 返回 clean=False 也会恢复。rollback 的 finally 无条件恢复，即使 restore 本身失败。

实际调用现有 release/rollback、只替换外部 Bench 和快照边界的最小复现：迁移后快照读取失败，`sites_unquiesced=[tenant.test]` 且没有部分报告；restore 失败，仍 `sites_unquiesced=[tenant.test]`。

修正：记录每站阶段；迁移后的异常、restore 异常或未声明差异应保留维护状态并落部分报告。只有完成且核验干净的结果才能按明确策略恢复访问。逐站开放与文档的“发布期间维护”口径也需一致，不承诺跨站原子回滚。

### R2 [P1] 同 tag 重跑覆盖唯一回滚基线

位置：`dsherp/admin.py:652–660,755–765,813–834`。

报告虽带时间戳，rollback 实际读取的 `releases/<tag>/<site>/before.json`、`backup.json` 却会被原子覆盖。第二次 release 同 tag 会用当前状态替换第一次发布前基线。

现有 release 的合成复现：同 tag 连续调用两次均成功，原基线 qty=2 被覆盖为 qty=3，backup.json 从 old-backup 改为 new-backup。

修正：保留不可覆盖的发布记录及备份关联，区分继续原尝试与新尝试。最短实现可先拒绝覆盖已有基线；如需重试，则复用原记录或使用显式发布尝试 ID。

### R3 [P1] 大表字段声明放行其他字段损坏

位置：`dsherp/release_compare.py:63–76,124–136`；`dsherp/release_snapshot.py:139–142`。

严格表超过 5,000 行后只留整行 hash。变化被表示为 field=None，而 `_declared` 的 `field is None and entry['fields']` 将它匹配到任意非空字段声明。

实际调用比较器复现：只声明 `Sales Order Item.item_name` 可变，保持名称不变、将 qty 从 2 改为 300，返回 **clean=True**，差异被归到名称变更 patch。

修正：无法证明变化属于声明字段时必须报未声明差异；严格表保留字段级证据，或在摘要不同后读取归档明细。新增列也应按共同字段比较，避免小表允许的 schema 扩展在大表因整行摘要改变而误报。

### R4 [P1] 租户权限与工作流数据被当作框架元数据排除

位置：`dsherp/release_snapshot.py:24–45,69–95`。业务依据：`frappe_app/dsherp_bridge/context_permissions.py:6,23–34`、`configuration_execution.py:95–107`。

Role、Custom DocPerm、Workflow 及其子表由 Frappe 定义，但记录可以由租户创建并决定权限与业务流程。它们不在 strict 清单，按模块归属会被整表排除。

本次只查指定 DocType 的少量元数据：Role/Custom DocPerm 属 Core，Workflow 及其子表属 Workflow；两个 Module Def 的 app_name 均为 frappe，DocType.custom 均为 0，实际符合排除路径。没有读取业务记录。

修正：复用本项目已有权限与配置事实清单，按记录归属区分租户数据和框架定义，至少覆盖发布器生成的 Workflow 及子表、租户角色、自定义权限。不要求把所有 Frappe 表无差别纳入严格比较。

### R5 [P1] 历史 patch 声明放行本次无关变化

位置：`dsherp/admin.py:623–635,713–718`。

当前遍历全部 patches.txt 收集 EXPECTED_CHANGES，没有核对本次实际执行了哪些 patch。历史声明会持续影响以后发布的 clean 判断。两个 patches.txt 当前为空，本机 DDL 演练未覆盖此路径。

修正：声明绑定本次执行的 patch 集合和发布记录，复用框架 Patch Log，并明确重复执行/失败 patch 的语义。用真实合成数据 patch 验证本次预期变化通过、历史声明不能放行无关变化。

### R6 [P1] 未绑定实际升级前镜像及回滚目标

位置：`dsherp/admin.py:742–748,808–818`；`deployment-runbook.md` 升级与回滚章节。

release 只比较参数与环境文件中的新 tag；rollback 只把当前环境 tag 抄进报告。发布记录没有升级前镜像身份，也不核对运行容器的实际版本。在新版本或错误旧版本容器中 restore，数据快照仍可能 clean 并恢复访问。

修正：明确旧版本与目标版本，记录并验证两个 bench 实际运行镜像的版本、提交和制品身份；备份及旧版本身份采集应在切换前完成。至少在本机隔离生产形态跑一次两个不同 tag 之间的升级/回滚。专用主机的正式 G2 可继续留作后续验收。

## 同批修正的快照边界

- **Single 新增值不等于新增 schema。** `release_compare.py:141–144` 忽略原快照不存在的字段，但 tabSingles 没该行可能只是已有设置未持久化。本次以已有 `System Settings.disable_user_pass_login` 从无存储值变为 1 的合成输入复现 clean=True。应区分新增字段与已有字段首次赋值。
- **Single 未应用密钥摘要。** `release_snapshot.py:147–151` 直接保留值；Data 类型 token/secret 可进入明文快照。应复用普通表的同一字段处理规则并补合成 Single 用例。
- **哈希约定未完整落地。** 行摘要 helper 重复、快照缺少摘要格式版本，新增哈希的五项论证未完整记录。场景可属于大对象检测和凭据摘要，但应统一实现、规范化输入及可解释诊断；论证本身不要求额外审批。
- **分页不等于内存受控。** 每页查询后仍把所有表的行/摘要累积到全站 dict，再一次性序列化。数据库单次读取压力已降低，不能据此声称内存风险消除。本次未做压力测试或 OOM 重现。可按表/页落盘并增量比较。
